# v1.0.4 최적화 모듈 준비 — 2026-10-22

13개 작업군을 모두 정리했다. 새 코드 모듈은 **9개**, 서로 다른 수정 대상 파일은 **14개**다. #8을 08a/08b로 나눴으므로 새 코드는 원래 작업군 8개에 해당한다. #1 Small은 이미 구현된 후보를 그대로 사용한다. #5·10·12·13과 #11의 추가 패스 병합은 상세 설계와 검증 조건까지 준비했으며, 적용 가능한 코드가 아직 없다.

현재 제품에는 적용하지 않았다. 선택 기준은 R이고 Small은 채택 전이다. 앱 표시 버전은 1.0.3, 작업상 명칭은 로컬 v1.0.4 실험 후보다. 실제 게임·GPU 실행, 제품 빌드, 성능 측정과 앱 삭제는 이번 준비에 포함하지 않았다.

## 적용·복원 단위

`modules/<이름>/module.json`에 각 파일의 정확한 이전/이후 바이트, SHA256, 모드, 정방향/역방향 패치가 있다. 원본 바이트는 중복 없는 `payload/`에 모았다. 08a는 R/Small 부모가 다르므로 서로 다른 패치를 사용한다.

같은 파일을 수정하는 **02↔04, 06↔07, 08b↔09**는 양쪽 순서의 중간 상태를 별도로 준비했다. baseline 패치 두 개를 억지로 겹쳐 적용하지 않는다. `QUEUE.json`의 `sameFileComposition`과 `complete-composition.json`에 정확한 조합이 있다. R/Small 각각 9개 모듈 전체의 정·역순 조합이 같은 결과를 만들고 원래 바이트로 복원되는 것을 메모리 안에서 확인했다. 이는 동시에 채택해도 성능이 좋아진다는 뜻은 아니다.

큐 사인 후에는 동결 R/Small 재비교의 결과와 부모를 먼저 확정하고, 준비된 코드부터 해당 증거 조건을 확인해 적용·관련 빌드·기능 검증·후보 패키징·성능 비교로 진행한다. 코드가 없는 네 작업군과 11b는 정해 둔 증거 수집·설계 절차부터 이어간다. 위험한 패스나 대기를 근거 없이 자동 삭제하는 기능은 없다.

실제 소스 적용 시 현재 파일 전체 해시가 정확히 맞아야 한다. 적용/복원 모두 현재 수정 시각을 갱신하여 변경된 헤더의 의존 파일이 다시 빌드되도록 한다. 기존 객체 파일을 새 헤더와 섞거나, 파일 시각을 과거로 되돌려 빌드를 건너뛰지 않는다. 실패한 측정은 자동 재실행하지 않고 원본을 남긴다.

## 완료한 검증과 남은 범위

- 16개 패치 변형의 정확한 적용·복원 및 다른 부모/중복 적용 거부 확인.
- 11a는 두 엔진×일반/HEADLESS의 CPU ASan/UBSan 검증. 실제 StreamBuffer와 추출한 Typed 경로, GL 문맥은 모의 객체다.
- 08a는 R/Small×Foundation 0/1, 각각 10개 시나리오·616개 확인. 실제 binding/pipeline 상태 갱신 코드, native 경계는 모의 객체다.
- 02는 9,798개, 03은 17,908개, 09는 49개 CPU 확인. 09에는 6개 동시 교체 일정이 포함된다.
- 04는 두 적용 순서 각각 Foundation 0의 817개·Foundation 1의 937개 CPU 확인. 마지막 수정은 주석뿐이며 이전 정확한 패치를 보존했다.
- 06/07은 기존 코드 332개, 06 332개, 07 355개, 결합 355개 CPU 확인. 실제 대기 조건·feedback·오류·완료 코드를 사용하고 native 이벤트/저장소 경계를 대체했다.
- 08b 최종 단독/09 결합 각각 2,216개 CPU 확인과 동시 교체 일정 3개. 최초 부분 재사용→반복 관찰 시 기존 전체 재생성→이후 전체 hit 전환을 확인했다. `_rejected`인 경우 부분 데이터 생성 비용이 반복될 수 있다.
- 최종 MoltenVK 모듈 결합에서 실제 5개 Objective-C++ 번역 단위를 Foundation 0/1로 구문 검사했다. 제품 객체·라이브러리·앱을 빌드하지 않았다.
- 구현자와 다른 검수자가 코드 또는 설계 경계를 검수했다. 검수 문서와 정확한 입력·결과는 같은 폴더의 `independent-*` 및 각 `receipt.json`에 있다.

이 검증은 실제 GPU 동작, 모든 race의 부재 또는 FPS 순이익을 보장하지 않는다. #4의 기존 native compact fixture는 앞선 Deferred 때문에 새 early 경로를 타지 않는다. 그 한계를 알고 별도의 좁은 실제 경로 확인을 남겼다. #8/#9는 추가 할당·참조계수 비용이 있으므로 유리한 작업량을 실제로 확인해야 한다.

테스트 입력의 전제 오류와 초기 실패 기록도 보존했다. 11a의 mock 크기 타입, 04의 compact capture 크기 조건, 08b 반복 관찰의 callback 도달 조건을 고쳤다. 실패 기록을 삭제하거나 실제 GPU 실패를 해결했다고 바꾸지 않았다.

`completion.json`은 이번 준비 결과, `frozen-inputs-final.json`은 보호된 앱·소스·벤치 상태, `publication-completion.json`은 원격 보존을 수행한 경우의 실제 커밋·검증 결과다. 원격 게시 여부는 그 영수증으로 판단한다.
